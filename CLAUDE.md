## Overview

Telegram bot that provides remote access to [Claude Code CLI](https://code.claude.com/docs) via Telegram messages. Pure Python (stdlib only), runs as a macOS launchd service.

## Architecture

```
User ↔ Telegram API ↔ claude-fallback-bot.py ↔ Claude Code CLI (subprocess)
```

### Files

| File | Purpose |
|------|---------|
| `claude-fallback-bot.py` | Main bot — Telegram polling, session management, Claude CLI orchestration |
| `claude-bot-menubar.py` | macOS menu bar indicator (requires `rumps`) |
| `claude-bot.sh` | Service manager — install/uninstall/start/stop/restart/status/logs |

### Runtime Data

All runtime data is stored in `~/.claude-bot/`:
- `sessions.json` — Session persistence (names, IDs, models, agents, message counts)
- `bot.log` — Application log (rotating, 5MB × 3 backups)
- `launchd-stdout.log` / `launchd-stderr.log` — Process output
- `routines-state/YYYY-MM-DD.json` — Daily routine execution state
- `chats.json` — Multi-tenant chat config (v3.49+): `{"primary": [...], "secondary": {chat_id: agent_id}}`. Managed via `/onboard`. See "Multi-tenant secondary chats" below.
- `agents/<agent>/settings.json` — Per-agent Claude CLI permission profile (v3.49+) used by secondary chats with `--permission-mode dontAsk`. Auto-generated by `/onboard`; safe to edit to tighten or relax the allow/deny lists.

When diagnosing bot issues, read `~/.claude-bot/bot.log` (last ~50 lines).

### Key Classes

- **`Session`** (dataclass) — name, Claude session ID, model, workspace, agent, created_at, message_count, total_turns, active_memory (per-session toggle, default `True`)
- **`SessionManager`** — CRUD for sessions, persists to `sessions.json`. `_load()` filters unknown keys so adding new fields is forward-compatible.
- **`ClaudeRunner`** — Spawns Claude CLI as subprocess, handles streaming JSON output, cancellation (SIGINT → SIGTERM → SIGKILL)
- **`ClaudeTelegramBot`** — Main orchestrator: Telegram long-polling, command routing, inline keyboards, message splitting

### How Claude CLI is Invoked

```python
runner.run(
    prompt=prompt,
    model=model,
    session_id=session_id,      # None for fresh sessions (routines always use None)
    workspace=workspace,        # cwd for the subprocess
    system_prompt=SYSTEM_PROMPT,# None when minimal_context=True
    agent_id=session.agent,
    restricted=False,           # True for secondary chats — see Multi-tenant section
)
```

The `ClaudeRunner` builds the command with `--print --output-format stream-json --input-format stream-json`. The **prompt is written to the subprocess's stdin** (one stream-json `user` message, then EOF) rather than passed as an argv positional: argv is readable by any local process via `ps` and is capped by ARG_MAX (1MB on macOS). A writer thread feeds stdin while `_read_stream` drains stdout, so a prompt larger than the 64KB pipe buffer cannot deadlock. By default the permission flag is `--dangerously-skip-permissions`. When `restricted=True` (multi-tenant secondary chat) it switches to `--permission-mode dontAsk --settings ~/.claude-bot/agents/<agent>/settings.json` so the agent runs against an allowlist scoped to its own vault directory. The `--append-system-prompt` instructs Claude to read the vault (Journal, Tooling, etc.) — it can be omitted via `system_prompt=None` when the routine uses `context: minimal`.

### Turn integrity (v3.81.0+)

Three contracts protect a single turn from being lost, leaked, or duplicated.

**A dead `--resume` is never passed.** A Claude transcript lives at
`~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`, so it is bound to the cwd
it was recorded under *and* pruned by the CLI after ~30 days. Resuming a missing
one does not degrade gracefully — the CLI exits with "No conversation found with
session ID", `num_turns: 0`, and the turn is spent on an error. `ClaudeRunner.run`
calls `_claude_transcript_exists()` first and runs fresh instead, setting
`runner.resume_dropped` so `_finalize_response` tells the user the history is
gone (a silent context loss just looks like the agent forgetting).

**The prompt never touches argv** — see the invocation note above.

**A Telegram send is never blindly retried.** The Bot API has no idempotency
key, so a retry after an *ambiguous* failure can deliver the same message twice.
`_tg_retry_is_safe()` splits on whether the failure proves the request never
left: urllib wraps connect/send errors (DNS, no route, refused, TLS handshake
timeout) in `URLError` → retry is free; a bare socket timeout comes from reading
the *response*, and a reset can land after the body flushed → Telegram may have
already delivered it, so the attempt stops and logs `delivery UNKNOWN`.
`_tg_http_retry_is_safe()` adds the status rule: 429 always retries, a 4xx is
final (three identical attempts only tripled the log noise), and a 5xx retries
only for methods where a duplicate is impossible. Reads and idempotent writes
(`getUpdates`, `editMessageText`, `deleteMessage`, `answerCallbackQuery`,
`sendChatAction`) retry either way.

Tests: `tests/test_turn_integrity.py` (32 tests).

**Failure reasons travel on a side channel.** `tg_request` still returns the
body or `None`, but every real call records a `TgResult` (status, description,
`retry_after`, `delivery_unknown`, `dropped`) readable via `tg_last_result()`
on the same thread; `send_message` records a per-chunk `_SendOutcome`
(`_last_send_outcome()`: `delivered|failed|unknown`). Built on that:
the plain-text resend happens **only** on "can't parse entities"; "message is
not modified" is a successful edit; a failed chunk stops the rest (no answer
with a hole); a `delivery UNKNOWN` send is never repeated.

**A final answer is never silently cut.** "Fits in one message" is measured
*after* HTML conversion. `edit_message(..., preview=False)` refuses to
truncate (returns `False`); only `preview=True` (stream/pipeline progress)
truncates. `_deliver_final_text` edits in place (with the copy-code button) or
sends the full text and retires the `⏳` placeholder (✅ or delete). The stream
message is unregistered/uncached only once delivery is settled: a transient
failure keeps both, posts a notice and retries once (`_handle_undelivered_final`);
restart recovery uses the same path.

**Rate limits.** `TelegramRateLimiter` paces send*/edit* per chat (private ≈1/s
with bursts of 3, groups 20/min) and globally (30/s), plus a per-chat
"do not send before" from a 429's full `retry_after`. Previews and chat actions
are *dropped* (never slept on) while a chat is throttled and cannot use the
last slots of a window; final deliveries wait up to `TG_MAX_RATE_WAIT` (90s).
Streaming edits in groups use `STREAM_EDIT_INTERVAL_GROUP` (4.5s).
`getUpdates` failures back off 5s→60s; a 409 calls `deleteWebhook` once and
alerts the primary chat (hourly throttle), as does a 401. The update offset is
written atomically. Tests: `tests/test_telegram_delivery.py`.

### Rich Messages (Bot API 10.1)

Model answers go out as **Rich Messages** — `sendRichMessage` / `editMessageText` with `rich_message: {"markdown": …}` — so tables, task lists, headings and collapsible `<details>` render natively and one message holds up to **32768 chars / 500 blocks** instead of 4096-char HTML chunks. It is strictly **opt-in per call site** (`rich=True` on `send_message`/`edit_message`): only the final answer (`_finalize_response`), the streaming preview (`_stream_updates`) and routine output use it; every internal status message keeps the HTML path. A message that already became rich keeps being edited as rich.

- **Fallback:** any rich failure lands on the existing HTML path — env off, kill switch tripped, API error (one HTML retry), or text above the rich limits (HTML split / document). An *ambiguous* `sendRichMessage` transport failure is **not** re-sent (same "delivery UNKNOWN" contract as `tg_request`).
- **Kill switch:** a 404 / "message text is empty" / "rich message must be non-empty" answer means the server doesn't understand rich messages → `_disable_rich_runtime()` turns it off for the process (WARNING, once). Three consecutive messages rejecting a rich edit disable rich *edits* only.
- **Markdown prep** (`_rich_markdown_from_model`): rich Markdown treats `$…$` as LaTeX, `==…==` as highlight, `||…||` as spoiler and a lone `~` as strikethrough, so those are escaped in prose (never in code or URLs).
- **Reasoning panel:** `_build_stream_display` opens the 🧠 block with `**>` → HTML `<blockquote expandable>`, rich `<details>` — collapsed by default on both paths.
- `sendMessageDraft`/`sendRichMessageDraft` streaming is **not** used (private chats only).

Tests: `tests/test_rich_messages.py`. The harness (`tests/_botload.py`) forces `RICH_MESSAGES=false` and `NOTIFY_DONE_AFTER_SECONDS=0`; those tests flip the module constants per case.

### v3.1 flat per-agent vault layout

Default workspace: `vault/main/` — the bot operates as the Main agent by default. Every session has an explicit `agent` string (defaults to `"main"`) and cwd is always `vault/<agent>/`.

```
vault/
├── CLAUDE.md        # universal rules + wikilinks to each agent hub
├── README.md        # root hub
├── Tooling.md       # shared
├── main/
│   ├── agent-main.md   # metadata (frontmatter) + hub wikilinks (body)
│   ├── CLAUDE.md       # personality/instructions (not a graph node)
│   └── Skills/, Routines/, Journal/, Reactions/, Lessons/, Notes/, workspace/
├── crypto-bro/      # same structure, isolated
└── parmeirense/
```

**Isolamento total:** no inheritance between agents. When a session is on crypto-bro, only `crypto-bro/Skills/`, `Routines/`, `Journal/`, etc. are discoverable.

**Agent detection.** A top-level directory counts as an agent if and only if it contains `agent-<dirname>.md`. That's the single source of truth — `iter_agent_ids()` (Python) and `iterAgentIds()` (Swift) use this rule. Reserved vault names (`README.md`, `CLAUDE.md`, `Tooling.md`, `Images`, `.graphs`, `.obsidian`) are never agents.

### Topic routing in a primary chat (v3.80.0+)

An agent claims a Telegram forum topic by declaring **both** `chat_id` and `thread_id` in its hub frontmatter. `_resolved_agent_for_chat()` resolves every incoming message in this order:

1. **Secondary-chat lock** (`chats.json`) — topic override, then that chat's default agent.
2. **Topic binding** (frontmatter `chat_id` + `thread_id`) — the agent that owns that topic.
3. **General topic** (`thread_id` absent) — the vault's **default agent** (`default: true` in frontmatter, normally Main), but only when the chat already has topic-bound agents.

Step 3 is what keeps the General channel clean. An agent can only claim a *named* topic, so before v3.80.0 General had no owner and kept whichever agent its session was last switched to — and `/agent new` switches the creating context, so creating an agent from General left that specialist answering there indefinitely. The rule is scoped to chats that already have topic-bound agents, so a plain single-room group still honors a manual `/agent` choice; secondary chats always use their own `chats.json` default and never inherit the vault default.

A manual `/agent <name>` still wins inside the General topic (`ctx._manual_override`), but that flag is in-memory only — after a restart General returns to the default agent. When auto-routing changes a session's agent, the Claude transcript (`session_id`) is reset: a transcript belongs to the cwd it was recorded under, so resuming it under another agent's workspace would point the CLI at the wrong project dir.

Routines follow the same ownership (`_find_context_for_routine`): an agent with frontmatter `chat_id` reports to its topic; the **default agent** reports to the General topic of the primary chat that has topic-bound agents, then the owner's private chat, then the first `TELEGRAM_CHAT_ID`. Contexts with an empty/`"0"` chat_id are never used (nor stored — `_get_context("")` returns a transient context), and a secondary chat is only used for the agent bound to it in `chats.json` — never as a generic fallback.

## Configuration

The project uses **two `.env` files with distinct purposes**:

### `~/claude-bot/.env` — Bot operational config

Read by `claude-fallback-bot.py` at startup and by ClaudeBotManager. Contains credentials and paths:

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `TELEGRAM_BOT_TOKEN` | Yes | — | Telegram bot token from @BotFather |
| `TELEGRAM_CHAT_ID` | Yes | — | Authorized Telegram chat ID |
| `CLAUDE_PATH` | No | `/opt/homebrew/bin/claude` | Path to Claude CLI binary |
| `CLAUDE_WORKSPACE` | No | `vault/main/` | Working directory for Main sessions |
| `CODEX_PATH` | No | `/opt/homebrew/bin/codex` | Path to OpenAI Codex CLI — required for any `gpt-*` model. Install: `brew install --cask codex`, then `codex login` with ChatGPT Plus/Pro |
| `ADVISOR_MODEL` | No | `opus` | Model used by `scripts/advisor.sh` when escalating |
| `MODEL_FALLBACK_CHAIN` | No | `opus,sonnet-5,haiku` | Fallback order when a model fails. Configurable via macOS app. |
| `DEFAULT_EFFORT` | No | `max` | Reasoning effort applied to Anthropic turns when nothing overrides it (`low\|medium\|high\|xhigh\|max`). Codex maps `max`→`high`. See `.claude/rules/multi-provider-models.md` |
| `MAX_CONTEXT` | No | `true` | When on, appends the `[1m]` 1M-context variant to native Anthropic models. **1M context requires pay-as-you-go usage credits enabled at claude.ai/settings/usage — even on subscription auth.** Without them the CLI rejects `[1m]`; the bot retries once on standard 200K context and then trips a process kill switch so subsequent turns skip `[1m]` (one wasted attempt per restart, no per-turn tax). Set `false`/`0`/`off` to skip the attempt entirely |
| `AUTO_COMPACT_WINDOW` | No | `400000` | Token window handed to the Claude CLI's native auto-compactor (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`) on every Anthropic run — the CLI compacts when context nears it (clamped to the model window, floor 100k). `0`/`off` = CLI default (full model window). See `.claude/rules/vault-runtime-features.md` |
| `OPUS_MODEL` / `SONNET_MODEL` / `HAIKU_MODEL` | No | — | Pin a concrete model id for that alias when the CLI's bare alias lags a release (this was needed for `OPUS_MODEL=claude-opus-4-8` while `--model opus` still resolved to 4.7 — `opus` now resolves directly to `claude-opus-5`). Unset → built-in default pins apply (`sonnet`/`haiku` → 5.5 ids, see `MODEL_ALIAS_DEFAULT_PIN`); `opus` uses the auto-tracking alias. Falls back to the alias if the pinned id is unavailable |
| `RICH_MESSAGES` | No | `true` | Deliver model answers (final edit, streaming preview, routine output) as Telegram Rich Messages (Bot API 10.1). `false`/`0`/`off` keeps the HTML path. See "Rich Messages" below |
| `NOTIFY_DONE_AFTER_SECONDS` | No | `20` | When a turn ran at least this long and its answer was delivered by editing the placeholder (edits never notify), send a short notifying "✅ Pronto · <duração>" reply to the user's message. `0` disables. Not sent for routines, `#voice` replies, cancelled turns, or answers already sent as new messages |

Edited via: ClaudeBotManager → Settings, or directly.

**Model versions auto-track upgrades.** The response signature shows the *real* model id the CLI reports at runtime (e.g. `claude-opus-5[1m]`) — captured from the init event, not a hardcoded map — so a model upgrade surfaces with zero code edits. Two upgrade paths: (1) the bare aliases (`opus`/`sonnet`/`haiku`) advance automatically when the installed CLI's alias mapping moves — keep the CLI current (the daily `update-check` routine flags brew/cask updates); (2) when a new model ships *before* the CLI alias catches up (as happened with Opus 4.8 — `--model opus` resolved to 4.7 for a while, while `--model claude-opus-4-8` already worked), pin it via `OPUS_MODEL` until the alias advances, then remove the pin (as of Opus 5, `opus` resolves directly — no pin is currently set). `MODEL_FULL_IDS` is only a display fallback for early failures / non-Anthropic providers.

### `vault/.env` — API keys for vault tasks

Read by Claude Code when executing tasks in the vault context. Contains keys for external services (Notion, Figma, etc.). **Does not contain** Telegram credentials or bot paths.

**Why separate?** `vault/` can be synced (iCloud, Git) — mixing Telegram tokens with third-party keys would be a security risk. Bot ops config stays local; workspace keys stay in the vault.

## Restart and Watchdog

### `/restart` command — `scripts/bot-self-restart.sh`

Called by the bot's `/restart` Telegram command. Uses `launchctl kickstart -k gui/<uid>/com.claudebot.bot` (atomic kill+restart on modern macOS). Falls back to `bootout`/`bootstrap` if the service is not registered.

- Touches `~/.claude-bot/.watchdog-notified` to suppress watchdog alarms during the restart window
- Polls for a new PID (max 40s) and confirms via Telegram when the new process is up
- **Do not use `launchctl load/unload`** — deprecated on Darwin 24+ and unreliable with `set -e`

To restart the bot manually from Claude Code:
```bash
bash /Users/viniciusramos/claude-bot/scripts/bot-self-restart.sh
```

### Watchdog — `bot-watchdog.sh`

Runs via launchd every 60s (`com.claudebot.watchdog.plist`). Checks `pgrep` for the bot process:
- **Bot running + flag set** → flag cleared + "voltou a funcionar" notification
- **Bot down + no flag** → flag set + restart attempt + "Bot caiu!" notification
- **Bot down + flag set** → silent (already notified, waiting)

Restart order: `launchctl kickstart` first (service registered), fallback to `launchctl bootstrap` (service unregistered after failed restart).

**Disable/enable:**
- Via Telegram: `/watchdog off` / `/watchdog on` / `/watchdog` (status)
- Via shell: `touch ~/.claude-bot/.watchdog-disabled` / `rm ~/.claude-bot/.watchdog-disabled`

Useful when doing manual maintenance to avoid spurious alerts and auto-restarts.

## Development Guidelines

- **No pip dependencies** for the main bot (`claude-fallback-bot.py`). Only stdlib.
- The menu bar app (`claude-bot-menubar.py`) requires `rumps`.
- Telegram API calls use raw `urllib.request` (no `requests` library).
- All Telegram message edits are rate-limited (`STREAM_EDIT_INTERVAL = 3.0s`).
- Long messages are split respecting Markdown code blocks.
- The bot validates `AUTHORIZED_CHAT_ID` on every incoming message — unauthorized messages are silently ignored.
- Plist files use `__HOME__` and `__SCRIPT_DIR__` placeholders — the install script (`claude-bot.sh`) substitutes them via `sed`.

## Multi-tenant secondary chats (v3.49+)

The bot supports multiple Telegram chats on a single instance — useful for sharing the bot with friends without giving them access to your personal group.

**Model:** secondary chats can host multiple agents — one per Telegram **forum topic** — with a **default** agent answering everywhere a topic isn't explicitly mapped (v3.50.0+). Two chat tiers:

- **Primary chat(s)** — your own group(s). Full access: any agent, all commands, `--dangerously-skip-permissions`. Seeded by `TELEGRAM_CHAT_ID` env var; auto-discovery still adds groups where an authorized user is present.
- **Secondary chat(s)** — your friends' groups. Each chat has a **default** agent and an optional map of `topic_id → agent`. Commands run an explicit **allowlist** (`SECONDARY_ALLOWED_COMMANDS`, enforced in `_handle_text` before dispatch): `/start /help /status /new /sessions /switch /clear /stop /btw /compact /cost /voice /lesson /important /save /skill`. Everything else — admin/global commands such as `/restart`, `/model` and the model shortcuts, `/effort` and `/audio` (bot-wide state), `/workspace`, `/timeout`, `/routine`, `/run`, `/delegate`, `/agent`, `/onboard`, `/doctor`, `/find` — answers "não está disponível neste chat". `/switch` still refuses another agent's session, `/help` shows `SECONDARY_HELP_TEXT`, and each secondary chat gets a chat-scoped `setMyCommands` menu (`BotCommandScopeChat`, also registered on `/onboard`). `/delegate` additionally passes `restricted=True` when invoked from a secondary chat (defense in depth). Subprocess runs with `--permission-mode dontAsk --settings ~/.claude-bot/agents/<agent>/settings.json`. Curation is admin-only — only the primary chat can create or rebind agents.

**`chats.json` schema (v3.50.0+):**
```json
{
  "primary": ["123"],
  "secondary": {
    "-1001234567890": {
      "default": "carol",
      "topics": {"100": "carol-coding", "200": "carol-fitness"}
    }
  }
}
```
Legacy v3.49 entries (flat `"<chat_id>": "<agent_id>"`) are migrated transparently on load. Saves always use the new format.

**New topics in secondary chats** trigger an automatic notification on the primary chat (no `/discovery` needed — the chat is already authorized). The first message in a new thread always cascades to the chat's default agent; the curator gets a card with `[➕ Vincular agente] [✅ Manter default]` and can pick an existing agent or auto-create one named after the topic title.

**Onboarding flow — preferred path (`/discovery`, v3.49.1+):**
1. From your **private chat** with the bot, run `/discovery` (default 10min, configurable up to 60min). State is in-memory, expires automatically, and `/discovery` is rejected on group chats so members of your primary group can't open the window.
2. Friend sends any message in their group. The bot detects the unknown chat, dedupes per `chat_id`, and notifies the chat where you opened the window with the group title, sender username, and `[➕ Vincular agente] [🚫 Dispensar]` buttons.
3. Click `Vincular agente` → pick an existing agent, or `➕ Novo agente` (auto-derives a vault-safe id from the group title; collisions get `-2`, `-3` suffixes). The shared `_onboard_chat` helper persists to `chats.json` and confirms.

Outside the discovery window the bot returns to silent-ignore for unknown chats — zero exposure surface.

**Onboarding flow — manual fallback:**
1. Friend creates a Telegram group and adds the bot. The bot logs `Ignoring message from unauthorized chat -100…` to `bot.log`.
2. You read the chat ID from the log and run `/onboard <chat_id> <agent_name>` in your primary chat. If the agent doesn't exist, a minimal scaffold is created at `vault/<agent_name>/`.
3. Friend's group is bound. Messages activate the locked agent automatically; the vault is isolated under `vault/<agent_name>/`.

**Per-agent permission profile.** When `/onboard` runs, it generates `~/.claude-bot/agents/<agent>/settings.json` with sensible defaults: allow file ops anywhere (cwd already pins it to the agent's vault), allow common safe Bash builtins, deny `Read/Edit/Write` against other agents' vault paths and against `~/.claude-bot/`, `**/.env`, `**/sessions.json`, `**/chats.json`. Edit the file to tighten or relax — the bot reads it fresh on each subprocess spawn.

**Isolation caveat (intentional, documented).** The deny list is enforced by Claude's permission system, which **does not sandbox Bash subprocesses**. A motivated user could still `cat ../main/something.md` from inside a Bash tool call. This is suitable for trusted friends, not adversarial users. For hard isolation, wrap the subprocess in `sandbox-exec` with a profile that denies file-read outside `vault/<agent>/` — not implemented yet.

**API cost.** Secondary chats use the same Anthropic auth as primary, so usage is billed to you. If a friend should pay, give them their own ZAI key and pin their agent to a `glm-*` model in `agent-<name>.md` frontmatter.

## Vault

The `vault/` directory is the bot's persistent knowledge base — an Obsidian graph with Journal, Notes, Skills, Routines, and Agents. See `vault/CLAUDE.md` for complete documentation of the vault structure and rules.

### Setup for new users

The vault's index files (`Agents/Agents.md`, `Routines/Routines.md`, `Journal/Journal.md`) are committed with placeholder content. First-time setup:

1. Edit the index files to reflect your own agents/routines
2. Create your `vault/.env` with your own API keys (gitignored)
3. Customize `vault/Tooling.md` with your tool preferences

Personal content of indexes SHOULD NOT be committed — keep local only.

## Context isolation

Claude Code loads ALL CLAUDE.md files in the directory hierarchy (from cwd to root + `~/.claude/CLAUDE.md`). To ensure the bot uses ONLY this project's instructions:

**`.claude/settings.local.json`** (gitignored):
```json
{
  "claudeMdExcludes": [
    "/Users/YOUR_USERNAME/CLAUDE.md",
    "/Users/YOUR_USERNAME/.claude/CLAUDE.md"
  ]
}
```

This blocks CLAUDE.md from other projects (e.g., OpenClaw) when Claude CLI runs with `cwd` inside this project.

**Dev/runtime separation:** This CLAUDE.md contains DEVELOPMENT instructions. `vault/CLAUDE.md` contains the bot's OPERATIONAL knowledge base. When the bot invokes Claude CLI with `cwd=vault/`, Claude sees primarily vault/CLAUDE.md. This file (from root) loads as parent in the hierarchy, but contains only development info — it doesn't interfere with bot operations.
